# Inventário de escritores e autoridade de persistência

Inventário para migração sem alterar semântica. Referências são caminhos/linhas do código atual; operações administrativas e scripts manuais não devem virar rotas ou rodar em produção por default. Nenhuma estratégia de rollback de dado é presumida: usar backup/snapshot e guardas/idempotência próprias antes de execução; preservar logs/contagens.

## Scripts de escrita administrativa e rollback operacional

`scripts/*.ts` contém writers one-off que não são APIs da aplicação. Busca estática encontrou pelo menos estes grupos explícitos (inventário deve ser mantido ao introduzir novos scripts):

- **Backfills lots:** `backfill*.ts`, `backfill-cidade-*`, `backfill-marca.ts`, `backfill-tipo-bem.ts`, `backfill-tipo-imovel.ts`, `backfill-classificacao-filtros.ts`, `backfill-kuss-lance-minimo.ts`, `backfill-doc-copart.ts`, `backfill-busca.ts`, `backfill-patio-limpo.ts`, `backfill-titulo-veiculo.ts`, `reparse-marca.ts`, `reclassificar.ts`, `reparar-acento-cidade.ts`, `rescrub.ts`. Alguns têm comparação before/after e write guard (`backfill-classificacao-filtros.ts`); não presumir os demais reversíveis.
- **Catálogo/domínios:** `descobrir-leiloeiros.ts`, `importar-leiloeiros-docx.ts`, `aumentar-mapeamento.ts`, `reconciliar-dominios-fenaju.ts`, `vps-discovered-sites.ts`, `validar-leiloeiros-downloads.ts`; alteram `auctioneers`/`discovered_sites`. `reviewed-sites-dryrun.ts` só emite SQL e comenta explicitamente que não executa UPDATE.
- **Reparo de lotes:** `reparar-links-kuss.ts` atualiza IDs/URLs/raw e pode encerrar lotes.
- **Scripts de teste:** `teste-*` podem criar dados locais; alguns usam `pg` fixture/transação própria, mas confirmar antes de executar.

Autoridade: operador com DB alvo conscientemente selecionado, não HTTP/admin usuário. Antes de executar qualquer writer manual: ler script completo, confirmar alvo host/database, snapshot/export antes, dry-run e contagem/guardas, janela de escrita autorizada, transação quando viável, preservar output de changed rows. Para rollback: script inverso com before-value ou restore de backup/snapshot; se não houver before-value/guard, registrar como não automaticamente reversível e parar para plano explícito. Nunca incluir credenciais/dados pessoais em logs ou artefatos; não usar banco produção para baseline/testes.

## Fronteiras recomendadas de persistência

- Domain: políticas e normalizadores puros; sem SQL/Prisma/Redis.
- Services de application: casos de uso e coordenação transacional. Um writer owner para upsert/bid-history, identidade, alerts/accounts e tenant attempts.
- Prisma client transacional para a transação de `upsertLots`; SQL raw reservado para consultas/expressões especializadas mantendo parâmetros, sem repository genérico.
- BullMQ/Redis lock/ownership, autorização de persistência e cancelamento são fronteira de I/O separada de transações PostgreSQL. Testar Redis real e PostgreSQL real separadamente.
- Datas/valor/IDs compatibilidade: hoje PG `numeric` + `int8` são coerced para JS `Number`; regra/API vê numbers (`core/db.ts:3-5`, `repo.ts:41-42,116-124,208-220`). Avaliar precisão decimal/BIGINT com testes e aceite específico; não introduzir `Decimal` silenciosamente.
